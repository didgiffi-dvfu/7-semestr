## 1. Процессы в Linux

### Идентификатор процесса
**PID** (process id) — уникальный числовой идентификатор процесса в системе.

### Правило Linux: процесс порождает процесс
Процесс может быть создан **только другим процессом**. Корень дерева процессов — `init` (в старых системах) или **systemd** (в современных), у него PID = 1. От него происходят все остальные процессы.

### fork — создание копии
Системный вызов **`fork()`** создаёт почти точную копию родительского процесса (дочерний получает свой новый PID).

Используется технология **Copy-on-Write (COW)**: сразу память не копируется — родитель и потомок делят одни и те же страницы, помеченные «только для чтения». Копирование конкретной страницы происходит лишь в момент, когда один из процессов пытается её **изменить**. Это делает `fork()` быстрым и экономным по памяти.

### exec — замена образа процесса
Семейство вызовов **`exec*()`** (`execvp`, `execve` и т.д.) загружает новую программу **поверх текущего процесса**:

- **сохраняется**: PID, часть открытых файловых дескрипторов, окружение (частично);
- **заменяется**: код, данные, куча, стек — всё берётся из новой программы.

То есть процесс не создаётся заново — он «перерождается» в другую программу. Классическая связка: `fork()` → в потомке `exec()`.

### Завершение процесса
Процесс завершается одним из способов:

- **нормально** — программа дошла до конца / вызвала `exit()`;
- **по сигналу** — например, `SIGTERM`, `SIGKILL`;
- **аварийно** — необработанная ошибка (например, `SIGSEGV`).

В ядре за завершение отвечает функция **`do_exit()`**. Она «оркестрирует» уборку:

1. процесс помечается как завершающийся;
2. освобождаются ресурсы (память, файлы — если этот процесс был последним, кто держал файл, файл закрывается);
3. все **дочерние** процессы передаются `init`/systemd (их «усыновляет» init или назначенный **subreaper**).

### Состояние «зомби»
После завершения процесс переходит в состояние **zombie**: код и ресурсы освобождены, но в таблице процессов остаётся запись (PID, код возврата и пр.). Она нужна, чтобы родитель смог прочитать код завершения.

Запись удаляется, только когда **родитель вызовет `wait()` / `waitpid()`**. Если родитель этого не делает — зомби «висит». Если родитель умер раньше потомка — потомок становится **сиротой**, и его усыновляет init/subreaper, который сделает `wait()`.

### Взаимодействие процессов (IPC)

**Pipes (каналы)** — однонаправленная «труба»: один процесс пишет во вход, другой читает из выхода. Если буфер заполнен — пишущий **блокируется**, пока читатель не освободит место.

**Сигналы** — асинхронные уведомления процессу (`SIGINT`, `SIGTERM` и т.д.). Ядро хранит **таблицу обработчиков сигналов**; процесс может задать свою реакцию (кроме `SIGKILL` и `SIGSTOP`).

**Сокеты** — **двунаправленные** каналы связи. Unix-domain сокеты работают внутри одной машины (как внутренняя сеть) и позволяют вести полноценный «диалог» между процессами; сетевые сокеты — между машинами.

### Изоляция и ограничение ресурсов

**Namespaces (пространства имён)** изолируют то, что процесс «видит»:

- **PID namespace** — свои идентификаторы процессов;
- **Network namespace** — свой сетевой стек (интерфейсы, порты);
- **Mount namespace** — своё дерево точек монтирования;
- **User namespace** — свои пользователи и права.

**cgroups (control groups)** ограничивают **ресурсы** (CPU, память, I/O). Namespaces отвечают за *видимость*, cgroups — за *потребление*. Вместе это основа контейнеров (Docker и т.п.).

## 2. Процессы в Windows

### Идентификатор процесса
**PID** тоже есть, но процесс в основном адресуется через **HANDLE** (дескриптор) — объект ядра, через который с процессом работают API-функции.

### Создание процесса: CreateProcess
В Windows **нет `fork()`**. Процесс создаётся сразу новой программой одним вызовом **`CreateProcess()`** (`CreateProcessW`). Он объединяет то, что в Linux делают `fork` + `exec`: создаёт новый процесс и **сразу** загружает в него программу.

На выходе — структура `PROCESS_INFORMATION`: **HANDLE процесса**, **HANDLE главного потока**, PID процесса и потока.

> Отличие от Linux: родитель и потомок **не** делят память по Copy-on-Write — это с самого начала независимые адресные пространства.

### Потоки как основа
Единица выполнения — **поток (thread)**, а процесс — это контейнер (адресное пространство + ресурсы), в котором живёт минимум один поток. В Linux исторически первичен процесс; в Windows акцент сильнее на потоках.

### Ожидание и код возврата

- **`WaitForSingleObject(hProcess, INFINITE)`** — блокирует поток, пока дочерний процесс не завершится (аналог `waitpid`). Есть `WaitForMultipleObjects` для нескольких объектов.
- **`GetExitCodeProcess(hProcess, &code)`** — получить код возврата (аналог `WEXITSTATUS`). Пока процесс жив — вернёт `STILL_ACTIVE`.
- **`CloseHandle()`** — закрыть дескрипторы процесса и потока, когда не нужны (иначе утечка хендлов). Явного «зомби» нет, но объект ядра держится, пока открыт хотя бы один HANDLE.

### Завершение процесса

- нормальное — `main`/`WinMain` вернула значение или вызван `ExitProcess()`;
- принудительное — `TerminateProcess()` (грубое, без корректной уборки);
- аварийное — необработанное исключение.

### Взаимодействие процессов (IPC)

- **Pipes** — **анонимные** (`CreatePipe`, аналог Unix pipe) и **именованные** (`CreateNamedPipe`, могут работать по сети, двунаправленно).
- **Нет сигналов в Unix-смысле.** Вместо них — **объекты синхронизации ядра**: события (`Event`), мьютексы (`Mutex`), семафоры (`Semaphore`), которых «ждут» через `WaitFor...`. Отдалённый аналог сигналов для консоли — `Ctrl+C`/`Ctrl+Break` и `SetConsoleCtrlHandler`.
- **Сокеты** — библиотека **Winsock** (`WSAStartup`, далее почти как POSIX-сокеты).
- **Разделяемая память** — через **File Mapping** (`CreateFileMapping` / `MapViewOfFile`).

### Изоляция и ограничение ресурсов

- **Job Objects** — объединяют процессы в группу, ограничивают ресурсы и позволяют завершать всю группу разом (ближайший аналог cgroups).
- **Security tokens / ACL** — права доступа привязаны к токену процесса.
- **Windows Containers / Server Silos** — изоляция уровня контейнеров, близкая к namespaces.

### Короткое сравнение

| | Linux / POSIX | Windows |
|---|---|---|
| Создание | `fork` + `exec` | `CreateProcess` (всё сразу) |
| Копирование памяти | Copy-on-Write при `fork` | Нет, сразу раздельная память |
| Ожидание | `waitpid()` | `WaitForSingleObject()` |
| Код возврата | `WEXITSTATUS()` | `GetExitCodeProcess()` |
| Уведомления | сигналы (`SIGxxx`) | объекты синхронизации, `Ctrl`-handlers |
| Ограничение ресурсов | cgroups | Job Objects |
| Изоляция | namespaces | Silos / Containers, tokens |

## 3. CMake

**CMake** — кроссплатформенная система автоматизации сборки. Из одного описания исходного кода она **генерирует** нативные файлы сборки под конкретную платформу:

- **Unix** — `Makefile` (сборка через `make`);
- **Windows** — проекты/решения для Visual Studio (`.sln`, projects);
- **macOS** — проекты для Xcode.

### Основы использования

Главный файл — **`CMakeLists.txt`**. Он описывает структуру и шаги сборки на уровне проекта и пишется на специальном языке CMake.

**Команды.** Синтаксис — `command(args)`. Имя команды **не зависит от регистра** (`set` = `SET`).

```cmake
set(VAR a b c)        # создать переменную-список из строк (разделитель — пробел)
set(VAR "a b c")      # одна строка целиком
```

**Использование переменной** — через `${VAR}`. При подстановке в команду список «разворачивается»:

```cmake
command(${VAR})       # эквивалентно command(a b c)
```

### Минимальный пример для этой лабы

```cmake
cmake_minimum_required(VERSION 3.15)
project(lab1 C)

# библиотека запуска процессов
add_library(proc proc.c)
target_include_directories(proc PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

# тестовая утилита, использующая библиотеку
add_executable(proc_test main.c)
target_link_libraries(proc_test PRIVATE proc)
```

Сборка (одинаково на Linux, macOS, Windows):

```bash
cmake -S . -B build
cmake --build build
```
