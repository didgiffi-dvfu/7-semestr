# Лабораторная работа 2 — подсказки

Кроссплатформенная (POSIX / Windows) программа: таймеры, общий счётчик в разделяемой памяти, синхронизация, порождение копий и выбор «лидера».

Что делает программа:
1. при старте пишет в лог свой PID и время запуска;
2. раз в 300 мс увеличивает счётчик на 1;
3. через CLI позволяет задать счётчику любое значение;
4. раз в 1 секунду пишет в лог время (с миллисекундами), PID и счётчик;
5. раз в 3 секунды порождает 2 копии (копия 1: +10; копия 2: ×2, через 2 с ÷2); если копия ещё не завершилась — пишет сообщение и не запускает новую;
6. при нескольких запущенных экземплярах счётчик модифицируют все, но логирует его и плодит копии только один — «лидер».

---

## 1. Многозадачность: процессы и потоки

**Процесс** — программа в своём отдельном **адресном пространстве** (своя память). **Поток (нить)** — ветка исполнения **внутри** процесса, нити одного процесса делят общую память (Лекция 2).

В нашей программе есть и то, и другое:
- **процессы:** каждый запуск программы — отдельный процесс; копии — тоже отдельные процессы;
- **нити внутри процесса:** главная (CLI), таймер 300 мс, логгер 1 с, спавнер 3 с.

Вывод: память между **нитями** общая сама по себе, а между **процессами** — нет, её надо организовать через IPC (разделяемую память).

---

## 2. Таймеры и работа со временем

Интервалы (300 мс / 1 с / 3 с) реализованы фоновыми нитями `std::thread`, которые «спят» нужное время (`std::this_thread::sleep_for`). Это модель программного таймера из Лекции 2: отдельный модуль отсчитывает интервал и выполняет задачу.

Время **с миллисекундами** (`time()` даёт только секунды!):

| | POSIX | Windows |
|---|---|---|
| момент с долями секунды | `gettimeofday()` (сек + мкс) | `GetLocalTime()` → `wMilliseconds` |
| разложить на дату | `localtime_r()` | уже разложено в `SYSTEMTIME` |
| PID | `getpid()` | `GetCurrentProcessId()` |

На POSIX микросекунды делим на 1000 → миллисекунды. В `struct tm` год считается от 1900 (`+1900`), месяц с нуля (`+1`); в `SYSTEMTIME` поля уже «человеческие».

## 3. Синхронизация: мьютекс, семафор, барьер

**Зачем.** `counter = counter + 1` — это три шага (прочитать → прибавить → записать). Если два потока/процесса делают это одновременно, один инкремент может потеряться — **состояние гонки** (Лекция 2). Поэтому доступ к общему счётчику — **критическая секция**, в неё пускаем по одному.

- **Мьютекс** (mutual exclusion) — «один ключ»: внутри критической секции только один. У мьютекса есть «владелец» (отпускает тот, кто захватил).
- **Семафор** — атомарный счётчик разрешений: `wait` (−1, захват), `post` (+1, освобождение). Семафор со значением **1** работает как мьютекс. Владельца нет.
- **Барьер** — точка сбора: задачи ждут, пока к ней подойдут все, и продолжают вместе. В этой лабе **не используется** (нужен для синхронного старта группы).

**Важно:** `std::mutex` синхронизирует только **потоки одного процесса**. Между **процессами** он не работает — нужны **именованные** межпроцессные примитивы:

| | Межпроцессный именованный лок |
|---|---|
| POSIX | только **семафор** `sem_open` (значение 1) |
| Windows | **мьютекс** `CreateMutex` (а также может быть семафор) |

## 4. IPC: разделяемая память

Механизмы IPC (Лекция 3): файл, сигнал, неименованный/именованный канал, **разделяемая память**, сокет.

Для общего счётчика выбрана **разделяемая память** — «самый быстрый IPC»: счётчик становится обычной переменной в общей области, которую правят все процессы. Канал/сокет — это потоковая передача (не подходит для «одного общего значения»), сигнал данных почти не несёт, неименованный канал доступен только родственным процессам.

| Операция | POSIX | Windows |
|---|---|---|
| создать/открыть | `shm_open` + `ftruncate` | `CreateFileMapping` / `OpenFileMapping` |
| подключить → указатель | `mmap` (`MAP_SHARED`) | `MapViewOfFile` |
| отключить | `munmap` | `UnmapViewOfFile` |
| удалить | `shm_unlink` (живёт до явного удаления) | исчезает, когда закрыт последний `HANDLE` |

Любое обращение к этой памяти — под именованным локом (см. раздел 3).

## 5. Порождение копий (отдельных процессов)

Копия — это **та же программа**, запущенная с аргументом `--child 1` / `--child 2`. В начале `main` проверяем аргументы: если это копия — выполняем её роль и выходим, обычный режим не запускаем.

| | POSIX | Windows |
|---|---|---|
| запустить копию | `fork()` + `execl()` (классика из Лекции 2) | `CreateProcess()` (fork+exec «в одном») |
| передать роль | аргумент `--child N` | аргумент `--child N` |
| «копия ещё работает?» (неблокирующе) | `waitpid(pid, &st, WNOHANG)` == 0 | `WaitForSingleObject(h, 0)` == `WAIT_TIMEOUT` |
| код возврата | `WEXITSTATUS` | `GetExitCodeProcess` |

**Зомби (POSIX):** завершившийся потомок висит в таблице процессов, пока родитель не сделает `waitpid`. Поэтому проверку живости делаем через `waitpid` — она же «пожинает» зомби. В Windows зомби нет, но нужно закрывать `HANDLE` (`CloseHandle`), иначе утечка.

**Пункт 5c:** перед запуском новой копии проверяем прошлую; если ещё жива — пишем сообщение в лог и не запускаем (на обычной скорости копии успевают завершиться за 2 с < 3 с, поэтому ветка срабатывает редко — это защита на случай «тормозов»).

## 6. Выбор лидера (пункт 6)

Запущено много экземпляров, но логировать счётчик и плодить копии должен **один** — лидер.

Решение: в разделяемой памяти хранится `leader_pid`. При старте (и периодически) процесс под локом проверяет:
- если `leader_pid == 0` **или** процесс с таким PID **мёртв** → записывает свой PID (становится лидером);
- иначе — остаётся обычным.

Проверка «жив ли процесс»:

| POSIX | Windows |
|---|---|
| `kill(pid, 0)` (не шлёт сигнал, только проверяет; 0 — жив) | `OpenProcess` + `GetExitCodeProcess` == `STILL_ACTIVE` |

Это даёт **автоматический перехват лидерства**: если лидера убить, следующий процесс в своём цикле увидит, что прежний мёртв, и займёт его место.

## 7. Общий лог-файл

В один файл пишут много процессов. Чтобы строки не «склеивались», файл открыт в режиме **дозаписи** и каждая строка пишется одним системным вызовом:

| POSIX | Windows |
|---|---|
| `open(..., O_APPEND)` + `write` | `CreateFile(FILE_APPEND_DATA)` + `WriteFile` |

Дозапись в конец на уровне ОС атомарна для коротких строк — этого достаточно.

## 8. Кроссплатформенность и сборка

- Платформенный код разделён: `src/unix/*` и `src/windows/*`; общий интерфейс — в `include/*.h`.
- В коде — `#if defined(_WIN32) || defined(_WIN64)`; в CMake — `if(WIN32) ... else() ... endif()`.
- На Linux `shm_open`/`sem_open` лежат в библиотеках **`rt`** и **`pthread`** — их линкуем (`target_link_libraries(... rt pthread)`); на macOS/Windows не нужно.
- В заголовках **не** писать `using namespace std;` (протекает и ловит конфликты, например `std::byte` против `byte` из `<windows.h>`); перед `<windows.h>` ставим `#define WIN32_LEAN_AND_MEAN`.

Сборка:
```bash
cmake -S lab_2 -B lab_2/build
cmake --build lab_2/build
./lab_2/build/test_runner
```

Запуск демонстрации «много программ»: открыть 2–3 терминала и в каждом запустить `test_runner` — счётчик общий, лидер (первый) логирует и плодит копии.

**Сброс разделяемой памяти на Linux** (если меняли структуру `SharedData` или нужен чистый старт):
```bash
rm -f /dev/shm/lab2_counter /dev/shm/sem.lab2_counter_lock
```

## Частые вопросы на защите

- **Почему разделяемая память, а не канал/сокет?** Счётчик — одно общее значение, которое правят все; канал доступен только родственным процессам, сокет/канал — это потоковая передача. Разделяемая память — прямой общий доступ, самый быстрый IPC.
- **Почему на POSIX семафор, а в Windows мьютекс?** По стандарту POSIX межпроцессным именованным может быть только семафор; в Windows именованным может быть и мьютекс. Семафор со значением 1 = мьютекс.
- **Почему не `std::mutex`?** Он неименованный, синхронизирует только потоки одного процесса; между процессами не работает.
- **Как узнаёте, что копия завершилась, не блокируясь?** `waitpid(..., WNOHANG)` / `WaitForSingleObject(h, 0)`.
- **Что если убить лидера?** Его PID в разделяемой памяти станет «мёртвым», и следующий процесс при проверке (`kill(pid,0)`/`OpenProcess`) перехватит лидерство.
- **Нужен ли учёт порядка байт/выравнивания?** Нет: все процессы — один бинарник на одной машине, раскладка одинакова. Это важно только при обмене между разными архитектурами (`htonl`/`ntohl`, XDR).
